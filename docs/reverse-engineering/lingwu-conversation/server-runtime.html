线程与 API 契约

GET

/api/state

返回 profile、status、threads、pending approvals、goals、settings、phone、hub、hands、holds、working 与 firstrun。它是 WebSocket hello 的快照来源。

GET

/api/threads/{id}/events

默认 200 条，limit 最大 1000；before 是事件 id，不是时间戳；返回 thread、events、has_more。

POST

/api/threads/{id}/send

text 最长 20,000；最多 10 个附件路径；language 与 via 最长 20。发送只入队，不等待模型完成。

POST

/api/threads/{id}/stop

返回 {"ok": bool}。线程不存在为 404；没有正在运行的 worker 时 ok=false，而不是错误。

POST

/api/threads/{id}/clear

仅空闲线程可清空；busy 时返回 409 thread is busy。

GET

/api/files/{path} 与 /api/files/upload

下载支持 Bearer 或签名票据；上传使用原始字节 body，文件名走查询参数，避免 multipart 依赖。

WS

/ws

首帧认证；支持 send、approval、device、device_result、ping；未知 kind 返回 error 而不是断开。

源码入口：lingwu/server/api.py:1-65 的路由说明，500-620 的认证与线程路由，1880-1970 的文件接口，2060-2145 的 WebSocket。

认证与文件票据

HTTP 认证

除健康检查等公开路径外，所有 API 依赖 Authorization: Bearer <token>。若请求仍携带旧的 ?token= 查询参数，会直接返回 401，并提示改用头部。

WebSocket 首帧认证

连接先 accept，再在 10 秒内等待 {"kind":"auth","token":"..."}；错误、超时、非 JSON 或错误字段都会关闭 4401。令牌不出现在 URL 中。

签名文件链接

img/iframe/video 无法附加 Authorization 头，因此前端用持有令牌生成 HMAC 签名：?exp=&sig=。签名绑定具体路径与过期时间，最多允许约 13 小时。

tickets.py 的 MAC 输入是 exp + "\n" + path，signature 截取 128 位十六进制；这样链接不会泄露原令牌，也不能跨路径复用。

安全边界：签名 URL 仍然会在浏览器缓存、历史和代理日志中留下“可访问一段时间”的能力链接。过期窗口与绑定路径限制了影响，但不等于短期令牌不可见。

WebSocket 命令面

SEND

发送消息

把文本截断到 20,000 字符，文件列表最多 10 个，语言和 via 截断到 20。异常会回 error，不关闭整个 socket。

APPROVAL

审批决定

支持本机审批与远端设备审批。远端审批失败返回 the device did not take the answer。

DEVICE

设备自报

手机通过 device 帧注册，服务端返回 device_ack 和手机状态，可用于后续屏幕操作。

PING

心跳

返回 pong 与当前整体状态，让客户端能区分“连接活着”和“线程在做什么”。

{"kind":"auth","token":"…"}
{"kind":"hello","state":{…}}
{"kind":"send","thread":"main","text":"你好","files":["attachments/2026-10-17/a.png"],"language":"zh-CN"}
{"kind":"approval","id":"ap_ab12cd34ef","approved":true,"scope":"once","reason":"…"}
{"kind":"ping"}
{"kind":"pong","status":{"state":"working","detail":"…","thread":"main"}}

一个独立的 pump 任务从 EventBus 队列读取消息并写入 socket；客户端命令也走同一把 asyncio.Lock，防止两个协程同时写 WebSocket 帧。

附件与产物链路

  1. POST /api/files/upload?name= 逐块读取 body，累计超过配置上限立即返回 413；空文件返回 400。
  2. 文件名只保留工作区安全字符，落到 attachments/YYYY-MM-DD/；同名文件自动加 (2)、(3) 后缀。
  3. 返回的 path 放入发送消息的 files；attachment() 再校验文件存在并补齐 name、size、kind、mime。
  4. Agent 的工具调用前会扫描工作区 mtime；非只读工具结束后再扫描，新增或变化文件变成 artifact 事件。
  5. 扫描超过 3000 个文件时放弃 diff，退化为只针对 files 工具的 write/append 参数播报产物。
  6. 同一轮里同一路径只创建一个 artifact 卡片，后续更新用 patch() 刷新，避免堆叠。

resolve_workspace_path() 对拼接结果执行 resolve()，并验证目标仍在工作区根目录内；越界抛 PermissionError，API 映射为 403。

事件适配器的隐藏工作

RUN

begin_run / end_run

清理上一轮的 stream、artifact、browser 卡片和模型标记；结束运行会把仍为 live 的浏览器卡片改为 done。

STREAM

临时流状态

按线程维护 stream id、buffer、last assistant text 与 event id；第一次 delta 才创建流，避免空回复产生气泡。

TOOL

工具芯片

工具调用创建 running chip，结果更新为 ok/error/blocked，并截断输出到 600 字符；tool id 映射保证原位更新。

ARTIFACT

工作区 diff

按 mtime 判断新文件或更新文件；产物事件只携带路径、文件名和动作，不把文件正文塞进时间线。

BROWSER

帧更新

最近帧保存在内存；同一轮复用一张 browser 卡片，通过 patch 更新 URL、标题、动作与帧 id。

HANDS/HOLD

外部执行状态

hands 任务按步骤 patch；hold 事件按 id 创建或更新，关闭时从活跃列表移除。

每条持久化事件会经过 Timeline.add()，随后 EventBus.publish()。如果 on_event 已注册，还会触发推送通知；hook 异常只记录日志，不阻断主事件流。

审批与用户问答

审批不是前端弹窗的局部状态，而是服务端 Future：

  1. ask_approval() 先注册 pending_approvals[approval_id]，再发出带 pending 状态的卡片，避免推送钩子读到“卡片存在但 Future 未注册”。
  2. 等待超时后自动生成拒绝决定，并把卡片 patch 为 expired。
  3. resolve_approval() 在时间线中找到卡片，写入 approved/denied、scope、decided_ts，再唤醒 Future。
  4. ask_user() 以线程为键维护一个问题 Future；用户下一条消息若命中 answer_question()，直接唤醒而不启动模型。

这解释了为什么审批卡片在刷新后仍能显示最终状态：运行中的等待由内存 Future 承担，展示与审计由时间线事件承担。

Agent 会话文件与重启修复

双层持久化

时间线面向 UI：用户、助手、工具、审批、产物。
session 文件面向模型：完整 Message 数组、turns、附件与工具调用结果。

两者不能互相替代：时间线可展示但不能直接作为模型上下文；session 保存模型历史但不包含全部 UI 卡片。

悬空工具调用修复

load_session() 会扫描 assistant 的 tool_calls，并补齐缺失的 tool 结果：“the app was restarted before this call finished”。否则很多模型提供商会拒绝整段历史。

stop_thread() 的取消路径也做同样收口：删除尾部未回答 tool 消息，或为每个工具调用补一条“Stopped by the user”结果。

{
  "saved_at": "2026-10-17T08:00:00+08:00",
  "turns": 12,
  "messages": [
    {"role": "user", "content": "…"},
    {"role": "assistant", "content": "…", "tool_calls": ["…"]},
    {"role": "tool", "tool_call_id": "…", "content": "…"}
  ]
}

进程内状态与磁盘事实的边界

状态存放位置重启后处理
运行中 worker内存 asyncio.Task消失；线程重新加载为空闲
inbox 排队消息内存 asyncio.Queue消失；未持久化消息不会重放
待审批 / 待回答Future + 时间线卡片卡片改为 expired
运行中工具时间线事件 + session状态改 error，session 补 tool 结果
浏览器 / hands内存帧 + 时间线卡片live 改为 done
hold内存 + 时间线改为 off，标记 stale
完整对话时间线 JSON + session JSON重新加载，可继续发送
恢复缺口：发送后、进入 inbox 前若进程崩溃，用户事件可能已经写盘但消息不会自动重新执行；重启不会重放未完成 turn，只保证历史可读与工具边界合法。

背压、并发与资源释放

  • 每个 WebSocket 订阅者独立队列，容量 1000；满时直接取消订阅，不等待消费。
  • 每个线程一个 worker，inbox 可排队；停止会清空队列并取消当前任务。
  • WebSocket 断开时 finally 取消 pump、退订队列、分离设备连接。
  • 时间线写盘通过 run_in_executor 执行，0.3 秒合并；关闭时 flush() 强制写盘。
  • 浏览器帧只保留最近若干个，避免无限增长；完整文件不在事件中。
  • 模型客户端在 turn 结束后释放；临时 Cloud 客户端在无其他线程引用时关闭。

这些机制保证单实例内资源有界，但不提供跨实例广播、跨实例线程锁或共享序列号。

服务端风险清单

  1. 广播队列按条数而非字节计，单条事件很大时仍可能占用显著内存。
  2. 时间线事件和 session 可短暂不一致：一个写完、另一个尚未写完时崩溃，会造成历史与模型上下文分叉。
  3. inbox 不持久化，进程重启会丢失已入队但未执行的用户消息。
  4. 工作区 diff 通过 mtime 判断，文件系统时间精度或外部同步工具可能造成漏报/误报。
  5. 签名文件链接在过期前可被转发；安全依赖短窗口和路径绑定。
  6. HTML 响应使用 CSP sandbox，而应用内查看器另有 iframe sandbox；两处策略需同步审查，避免一处放宽。
  7. WebSocket 命令没有显式请求序号；客户端重发 send 可能造成重复用户消息，除非上层有幂等键。

服务端深潜基于只读源码静态阅读；不包含真实并发压测、崩溃注入或生产代理验证。
