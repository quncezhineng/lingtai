一句话还原技术方案

01 · SUBMITHTTP 发送消息，先写入用户时间线事件，再入线程 inbox。
02 · RUN每线程单 worker 串行执行，busy 状态阻止并发覆盖。
03 · STREAM首次文本增量发 stream_start，后续发 delta，结束发 stream_end。
04 · RECONCILE持久化 assistant 事件替换临时气泡，前端重连后重载时间线。

关键设计判断

  • 事件溯源优先：对话不直接以“消息数组”驱动，而是以线程时间线事件为事实源，用户、助手、工具、审批、问题、产物都统一成事件。
  • 推送与持久化双通道：WebSocket 负责低延迟广播，JSON 时间线负责刷新、重连和重启后的恢复。
  • 流式气泡与最终气泡分离：临时流只用于增量显示，最终 assistant 事件复用流 ID 完成原子替换。
  • 慢消费者隔离：每个 WebSocket 客户端独立队列，队列满即移除订阅者，避免服务端内存无界增长。
  • 安全预览：HTML 产物在无 allow-same-origin 的 sandbox iframe 中渲染，脚本无法读取应用令牌或调用同源 API。

上游方案的优势与缺口

可复用优势

  • 按线程隔离，天然避免不同对话的流互相污染。
  • 时间线有 2000 事件上限与合并写盘，兼顾积压与磁盘开销。
  • WebSocket 首帧认证，避免令牌进入访问日志。
  • 前端在重连后刷新当前线程，能补齐断线期间已持久化的内容。
  • 滚动跟随使用 120px/400px 双阈值与 ResizeObserver，能处理气泡高度后增长。

静态分析发现的缺口

  • 上游 delta 没有独立序号，断线后无法只请求“缺失后缀”，只能重载整段时间线。
  • onopen 即重置重试次数；若服务端打开后立即关闭，会形成高频重连。
  • 广播是进程内的；多实例部署缺少共享 pub/sub 与跨实例顺序保证。
  • 流式增量未持久化，持久化的是完成后的 assistant 事件；进程崩溃时的半截回复不可恢复。
  • 附件与对话流共享时间线，但大文件本体不在事件内，只保存工作区路径。

当前项目的落地映射

当前工作区已经沿“可重放 SSE 账本”方向完成系统性改造：以 AG-UI 事件作为上游事实，镜像到带序号的 SSE 流；客户端按序号去重、补洞、重连，并以持久化消息完成完整性校验。
