Artifact 02 · Business logic

核心业务逻辑与状态机

对话模块真正的复杂度不在“调用模型”，而在发送前后的副作用排序：先可见、再排队、串行执行、增量展示、最终替换，以及失败、停止、清空和重启后的状态收口。

总览 架构依赖 交互流程 服务端运行时 前端渲染 REA 证据 分析数据

消息发送主链路

入口为 POST /api/threads/{id}/send，最终落到 MuseService.send()。以下顺序是理解消息一致性的关键。

1

校验与规范化

text.strip()；附件通过 self.attachment(path) 解析；文本和附件同时为空则抛出 ValueError("empty message")。

2

解析一次性云端模型

via="cloud" 时调用 cloud_once()，把本轮使用的客户端和模型 id 绑定到 inbox 项；未登录会抛 CloudError。

3

线程路由与语言记忆

找到或创建线程；把客户端语言写入 thread.agent.ui_language。若线程绑定其他设备，则改走 hub.run_remote()，不在本进程运行模型。

4

生成用户可见事件

构造 {"type":"user","text":...}，附带附件、模型标识、设备来源等字段，通过 ui.emit() 写入时间线并广播。

5

旁路拦截

如果消息命中待回答问题，answer_question() 直接消费并返回；如果命中 avatar 工作室请求，也由对应卡片处理，不启动模型。

6

线程元数据同步

发布 kind=thread 更新侧栏时间；通过 sync.message_sent() 尽早同步到账号其他设备，而不是等整轮结束。

7

进入 inbox

把普通文本或 Incoming 对象放入 thread.inbox，随后 _ensure_worker() 确保仅有一个未完成的 worker。

8

返回事件句柄

API 返回 {"event": event, "thread": thread.meta()}；客户端立即拿到用户气泡 id，后续助手内容通过推送通道到达。

线程状态机

idle无执行中的 run
workingworker 正在执行模型或工具
waiting等待审批或用户回答
stopping已请求取消，等待收口

thread.busy 是比 UI 状态更直接的门禁：worker 消费一条 inbox 项时置为 true，在 finally 中置回 false 并发布线程元数据。清空线程要求 not thread.busy，否则返回 false，由 API 映射为 409。

while not thread.inbox.empty(): item = thread.inbox.get_nowait() thread.busy = True status = "working" try: final = await thread.agent.run(...) finish_run(...) except CancelledError: settle_stopped(...) raise except Exception as exc: emit(failure_notice(exc)) finally: end_run() release_llm() thread.busy = False status = "idle" publish(thread.meta())

这套结构的核心不变量是：同一线程同一时刻最多一个 worker，但 inbox 可以继续接收排队消息；停止操作清空队列并取消当前 worker。

流式回复的生成与收口

WebUI.on_text_delta() 是流生命周期的起点。第一次收到非空文本时创建 stream_id，并把 stream 事件直接发到 EventBus；这些增量不写入时间线。

on_text_delta(text): thread = current_thread() sid = stream_ids.get(thread) if sid is None: sid = new_id("a") stream_ids[thread] = sid stream_buf[thread] = "" publish({kind: "stream_start", thread, id: sid}) stream_buf[thread] += text publish({kind: "delta", thread, id: sid, text}) on_assistant_message(content, reasoning): sid = stream_ids.pop(thread, None) text = (content or "").strip() if sid is not None: publish({kind: "stream_end", thread, id: sid, discard: not text}) if text: emit({id: sid or new_id("a"), type: "assistant", text})

为什么最后要复用同一个 id

前端把临时流维护为 state.streams[thread]。当持久化 assistant 事件以相同 id 到达时，reducer 可以在同一次更新中清除临时流并把正式消息插入事件列表，避免“先消失再出现”的闪烁。

stream_end.discard 的语义

如果模型先流出了内容，但最终被判定为空（例如被解析器移除的提示模式工具调用、静默后台运行），服务端发送 discard: true，前端立即删除临时气泡，不把无效内容留在界面上。

失败与取消

异常路径不伪造 assistant 消息，而是发出 notice 事件。取消路径由 _settle_stopped() 清理未完成的工具调用、重建合法消息边界、把 agent 状态归零并写入 “Stopped.” 通知。

停止、清空与重启修复

停止正在执行的线程

stop_thread() 先清空 inbox，再把最近 50 条事件中仍为 pending 的审批/问题标记为 expired，设置 thread.stopping = True 并取消 worker。取消后的会话必须移除悬空 tool message，避免下一轮模型看到“没有结果的工具调用”。

清空已完成的线程

clear_thread() 仅在空闲时执行：清空 timeline、重置 agent、保存 session、释放 holds、结束 sentinel 对话，并广播 thread_cleared。

进程重启后的修复

_make_thread() 加载时间线后，把遗留状态统一收敛：pending 审批/问题改为 expired；running 工具改为 error 并标记 “interrupted by a restart”；live 浏览器/hands 改为 done；内存中的 hold 改为 off 且标记 stale。

这一点很重要：时间线是事实源，但“正在执行”属于进程内状态，重启后不能假装它仍在运行。

文件产物业务链路

  1. Agent 将文件写入线程工作区，并产生 artifact 事件，包含 path、name、action。
  2. 时间线持久化产物事件；前端在 files 集合中汇总当前线程所有产物路径。
  3. ArtifactCard 展示标题、路径和类型；HTML/图片显示缩略预览。
  4. 点击卡片调用 onOpenFile(path)，由 FileViewer 读取文件文本或 URL。
  5. HTML 通过 srcDoc 进入 sandbox iframe，且不授予 allow-same-origin；脚本无法读取令牌或调用应用 API。
  6. Markdown 回复中若提到该线程已有的文件路径，会渲染成内部按钮，而不是跳转到外部地址。
产物卡只保存路径，不把文件正文塞进 WebSocket 事件。这避免大文件放大每条实时消息，也把访问控制留在文件读取 API 与查看器边界。

业务不变量

I1 · 先可见，再执行。 用户事件在 worker 启动前写入时间线，因此网络抖动或模型失败不会让用户的话消失。
I2 · 一条线程一个执行者。 _ensure_worker() 只创建一个未完成 worker，inbox 承担排队；避免两个 run 同时改写同一 session。
I3 · 临时流不落盘。 delta 仅广播，最终 assistant 事件才持久化；这使时间线保持较少记录，也意味着崩溃时不能恢复半截流。
I4 · 最终事件复用流 id。 保证客户端能把“直播气泡”原子替换为“正式消息”。
I5 · 慢客户端被隔离。 EventBus 队列满即断开，恢复责任转交给客户端的历史重载。
I6 · 重启状态必须收敛。 pending/running/live/hold 在加载时转为终止态，不把进程内执行幻觉带入新进程。
