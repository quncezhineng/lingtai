# Localization (i18n)

The mobile app (iOS, Android, and the web preview) ships with a small, dependency-free
localization layer. It covers every piece of interface chrome — navigation, screens,
sheets, tool cards, empty states, buttons, accessibility labels, and date/time formatting —
and lets the user switch language at runtime without a reload.

## Supported languages

| Locale code | Display name | `Intl` tag | Notes |
| --- | --- | --- | --- |
| `en` | English (`EN`) | `en-US` | Source of truth. Every key must exist here first. |
| `zh-Hans` | 简体中文 (`中`) | `zh-CN` | Simplified Chinese. Must mirror the English key set exactly. |

The product name **LingTai** is always rendered as **灵台** in Simplified Chinese. The single
source of truth is the `common.agentName` key; `localizeAgentName()` maps the server's
English default (`LingTai`) to the active locale while leaving user-renamed agents untouched.

## Architecture

All localization code lives in `apps/mobile/src/i18n/`:

| File | Responsibility |
| --- | --- |
| `types.ts` | `Locale` union, supported locale list, storage key, labels, `isLocale()` guard. |
| `locales/<locale>/*.ts` | Flat, namespaced dictionaries (see below). |
| `locales/<locale>/index.ts` | Merges the namespace files into one dictionary per locale. |
| `translate.ts` | Pure, React-free translation core: `translate()`, `tr()`, `setActiveLocale()`, `resolveLocale()`, `detectDeviceLocale()`, `statusLabel()`, `localizeAgentName()`. |
| `index.tsx` | `I18nProvider` + `useTranslation()` hook, and the re-exports consumed by screens. |
| `storage.ts` / `storage.native.ts` | Cross-platform persistence (web `localStorage`; native file system). |
| `LanguageSwitcher.tsx` | The header button and language menu. |

### Dictionaries

Each locale is split into namespace files so a feature's copy stays together:

`common`, `app`, `ui`, `chat`, `agent`, `screens`, `details`, `computer`, `threads`, `tools`, `status`.

Keys follow the `<namespace>.<semantic>` convention, e.g. `app.navChat`, `chat.placeholder`,
`status.awaiting_review`. English is authored first; `satisfies Dictionary` plus the unit
tests guarantee that `zh-Hans` has the identical key set — a missing or stray key fails
`pnpm typecheck` or `pnpm test`.

### Runtime

`I18nProvider` holds the active locale, persists changes, exposes it through
`useTranslation()`, and syncs the web document (`<html lang>` and the tab title) through
`syncDocumentLocale()`. `useTranslation()` returns `{ locale, t, setLocale }`; `t(key, params)`
interpolates `{name}`-style placeholders and falls back to English, then to the raw key.

Some helpers are rendered outside React (dates, relative times, enum labels). Those read the
module-scoped `activeLocale` via `tr()` / `activeLocaleTag()`, which `I18nProvider` keeps in
sync on every switch — so pure functions re-localize on the next render after a language change.

### Domain labels

- `statusLabel(value)` turns a domain enum (`awaiting_review`, `succeeded`, …) into display copy.
  Registered values come from the `status` namespace and follow the language; unregistered
  values fall back to "underscores → spaces, first letter capitalized".
- `localizeAgentName(name)` resolves the agent's display name, mapping the server default to the
  active locale (`LingTai` → `灵台` in Chinese) and passing user-renamed values through unchanged.
- `activeLocaleTag()` returns the `Intl` tag used by `toLocaleDateString` / `toLocaleTimeString`
  and the relative-time formatter.

## Persistence

The user's choice is stored under the key `lingtai.locale`:

- **Web** — `window.localStorage`.
- **Native** — a small JSON file in the app's document directory (via `expo-file-system`).

On startup the app reads the stored value; if none exists it falls back to the device locale
(Chinese → `zh-Hans`, otherwise `en`). An explicit switch always writes the value, so the
preference survives a reload on all three platforms.

## Adding a language

1. Add the new code to `Locale` and `LOCALES` in `types.ts`, and a row to `LOCALE_LABELS`.
2. Copy `locales/en/` to `locales/<new-locale>/` and translate every value (keep the keys).
3. Register the dictionary in `locales/<new-locale>/index.ts`.
4. Add the `Intl` tag in `LOCALE_TAGS` (`translate.ts`) and the storage/branching logic if needed.
5. Extend `apps/mobile/test/i18n.test.ts` so the new locale is covered by the key-parity and
   placeholder checks.

## Language switcher

`LanguageSwitcher` renders in the top navigation bar, next to the notifications bell. It shows
the active language's short label (`EN` / `中`) and opens a menu listing every supported language;
selecting one updates the UI immediately, persists the choice, and closes the menu.

## Testing

`apps/mobile/test/i18n.test.ts` (run through `pnpm test`) asserts:

- English and Simplified Chinese have identical key sets and matching `{placeholder}` sets.
- Interpolation, locale resolution, and device-locale detection behave as documented.
- `statusLabel()` and `localizeAgentName()` follow the active language, including the
  `LingTai` → `灵台` mapping and the "no `LingTai` left in the Chinese dictionary" guard.

## Known limitations

Some text visible in the app is **generated by the server** and stored as data rather than
authored in the client dictionary — for example activity titles such as *"Ready for your
review"* / *"Your details are needed"*, and model replies. These follow the server's language,
not the client switcher. Localizing generated content is a server-side concern and is out of
scope for the client i18n layer.
